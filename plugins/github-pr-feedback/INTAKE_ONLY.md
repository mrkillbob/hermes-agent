# Intake-only capability

This source candidate introduces `github-pr-feedback scan-intake --repository <approved repository>` through Hermes plugin command registration. It is disabled by default. The host's explicit plugin deny continues to take precedence over registration. No source change removes that deny or changes an existing scheduled job.

The independent capability requires `intake_only: {enabled: true}`, broad `enabled: false`, and `auto_dispatch: false`. The baseline source and candidate do not apply these settings. Any explicit `intake_only` section selects the new command tree and registers no completion hooks, repair controllers or maintenance commands, even when its flag is false or malformed. With that section absent, legacy protective completion hooks remain available; broad commands still require their master gate. Stored broad handlers reject whenever the explicit section is present or the master gate is false. Intake uses only the existing ordinary GitHub bot identity; Actions credential selectors are neither read nor passed.

Intake is limited to an unfenced registered control plane. The frontdoor binds the expected root through the public PluginContext passive snapshot capability and checks active native root, native Kanban home and any control-home override before policy loading and again immediately before credential access. Each adapter lookup, legacy lookup and create rechecks those roots and the native board-fence predicate. Worker/delegation identity fields and DB/workspace/attachment pins are refused by presence, including empty or false-valued strings; they are never stripped or overridden. This deliberately also holds nonworker DB overrides. An ordinary nonfenced HERMES_KANBAN_BOARD value remains allowed because each operation supplies its explicit approved board. The real adapter requires an explicit expected root and actual public context capability; it cannot infer registration authority from ambient state. Both the plugin and generic host check protected marker presence. Host-isolated contexts refuse this capability because child native fences cannot be safely transferred. Metadata-only replies have `tasks: null` and never prove task absence.

Existing repository/head-owner/branch restrictions, reviewer trust, bot/self policies and original `not_before` remain admission requirements. Retrieval must finish completely before any delivery. Missing access, malformed/truncated feedback and head changes return nonzero. No actionable admitted feedback returns success without a card.

Cards use the `github-pr-intake:v1:` namespace and `PR feedback intake:` title. They contain typed read-only metadata, exact head, feedback permalink, reviewer/time and body digest; raw feedback instructions are excluded. Creation is pinned to the existing directory workspace, Triage and `task-intake-router`. No model/provider/branch/reasoning/skills/goal or dispatch override is supplied. A durable acknowledgment must match the expected card and show no active claim/run/worker or execution override. Existing cards, including archived matches, are never edited or recreated.

A private 0700 receipt directory, 0600 files, cross-process lock and durable pending receipt precede create. Acknowledgment loss holds the receipt; an absent pending or uncertain card is never automatically recreated. A private identity index preserves completed-any-head deduplication and holds uncertain deliveries on older heads. An external digest anchor detects partial loss and database-only rollback. This is not protection against coherent deletion/restoration of all authoritative state. Preserving intact state and stopping the legacy writer are release preconditions.

Legacy reconciliation reads the existing `github-pr-feedback/ledger.sqlite3` with SQLite `mode=ro`; it never constructs the mutating legacy ledger class. Completed feedback on any head is already delivered; claimed/failed/ambiguous state holds. Missing or corrupt provenance holds. Before first delivery, passive host lookup must prove absence of matching legacy cards across all heads, including archived and intent-review cards; malformed or unclassifiable historical formats hold the board. Normal SQLite read-only access can create WAL sidecars, so this contract concerns task/schema data and does not promise zero filesystem effects.

The reviewed host must expose `ctx.kanban_readonly_snapshot(board, idempotency_key=... / idempotency_prefix=...)`. The generic host reads a complete bounded snapshot; all feedback receipt formats, hashes and legacy body qualification live in this plugin. Legacy snapshots retain the 10,000-row/8 MiB scan/1 MiB row/one-second bounds and filtered results retain the 1 MiB bound. There are no feedback-specific core CLI selectors. Old or host-isolated contexts fail closed with no fallback to mutating `list`, `show` or the broad Kanban client. A later release requires source review, qualified host dependency, intact/quiescent legacy state and separately authorized normal-path validation. Offline synthetic tests do not establish actual GitHub access, historical data parseability or restored scheduling.
